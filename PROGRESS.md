## How to run
Requirements: Python 3.12, Node.js 20.19+ (Vite 8). Windows or macOS.
```bash
python -m venv .venv
# Windows: .venv\Scripts\activate   macOS: source .venv/bin/activate
pip install -r backend/requirements.txt
cd frontend && npm install && cd ..
cp .env.example .env              # optional: everything has safe demo defaults
python scripts/seed.py --reset   # ~25 s incl. ~250 historical invoices; --no-history for a bare DB
python scripts/tamper_demo.py   # optional: break the audit chain; --restore to undo
python run.py                     # backend :8000, frontend :5173 (Ctrl+C stops both)
cd backend && python -m pytest    # 205 tests (about 90 s; the last file resets via the admin endpoint and runs the demo check)
cd frontend && npm run typecheck
python scripts/demo_check.py      # 28-step green/red table, isolated temp DB, AI offline (~45 s); exit 1 on any failure
cd frontend && npm run e2e        # Playwright: WCAG 2.1 AA scan of 23 screens + demo path (own stack on :8100/:5180, ~2 min); first `npx playwright install chromium` or set PW_CHANNEL=msedge
python scripts/demo_prestage.py --reset   # stage DB: reset + background scenarios S02 S03 S09a/b S10 S11 S12 (see docs/DEMO_SCRIPT.md)
python scripts/generate_invoices.py   # only to regenerate demo/invoices + demo/manifest.json
```
- Open http://localhost:5173. With `DEMO_MODE=true` (default) the login page lists one-click demo personas.
- Seed: 14 users, demo password `Duly@2026` for all (synthetic). API docs at http://127.0.0.1:8000/api/docs.
- After any model change, re-run `python scripts/seed.py --reset` (no migrations yet).
- Demo files: `demo/invoices/` (12 scenarios, 13 files: S9 has a and b) and `demo/manifest.json` (upload as whom, expected result, next step). Upload them in manifest order after a fresh reset.
- Python 3.12 is required (3.13+/3.14 lack wheels for some pinned packages, e.g. rapidocr-onnxruntime). On Windows: `py -3.12 -m venv .venv`.

- Demo persona login is a server endpoint (`/api/auth/demo-login`) that exists only when DEMO_MODE=true, so no password is embedded in the frontend. It skips password and lockout by design (demo only).
- Cross-tenant access returns 404 (not 403) so a supplier cannot probe which invoice ids exist.
- Login events are not yet in the audit trail: the hash-chained audit log is Phase 1 step 10; wire login/logout events then.
- Fictional bank names and IFSC prefixes (SHYG, NRMD, KVRG) and `.example` email domains so no seed value points at a real entity. RBI bank rate in policy (5.75%) is an editable assumption, to be verified.
- Document viewer uses server-rendered page PNGs (`/api/invoices/{id}/pages/{n}.png`, pdfium, cached in `backend/data/pages/`) instead of pdf.js in the browser: one code path for PDFs and photos, bounding boxes (page fractions) line up exactly, no pdf.js worker to break offline. Deviation from spec section 8 (react-pdf).
- Offline parser targets our generated invoice layout plus label variants; it is the "AI: offline (OCR)" path. Free-text fields (supplier name, descriptions) may lose spaces under OCR; suppliers are identified by GSTIN, never by name.
- Extraction results are append-only: a human correction adds a new row with source=manual; the latest row per field wins.
- Bank account numbers are masked in `extraction_results`; the full number is only stored encrypted on the invoice.
- HSN/SAC rate table (`validation/hsn.py`) is a labelled assumption; ambiguous codes list every allowed rate.
- Bank change maker is the AP clerk, checker is an approver (finance manager or above); the requesting supplier and the maker can never be the checker. Approval is impossible before the cooling period ends (use Demo controls to advance the clock in a demo).
- INJECTION_ATTEMPT is a FLAG (a person looks), not a BLOCK: the text has no power over the decision anyway; if the same invoice also has a real problem (e.g. bank change in the text AND on the invoice) the BANK_MISMATCH block still applies.
- QR decoding uses **zxing-cpp** (pip wheel, no system packages) with OpenCV as fallback. Measured: OpenCV failed to decode some IRP-size (version 21) QRs even from a perfect image, depending on the payload; zxing-cpp decoded 12/12 rendered invoices at 150-300 dpi plus a tilted, blurred photo. Deviation from spec section 5 C2 (OpenCV QRCodeDetector), recorded for reliability.
- Sample e-invoice QR is drawn as vectors (reportlab QR widget) in a clear bottom-left block; overlapping text had corrupted both the QR and text extraction.
- Controls report results: `no_activity` when nothing in the period could test the control (e.g. no approved invoices); never reported as a pass. C-02 checks "no override of a BLOCK" (overriding a sent-back APPROVE or a FLAG is allowed).
- Supplier-facing text has one source: `frontend/src/i18n/{en,hi}.json`, read by the backend too (chat offline answers, tool payloads). Add new keys there.
- Chat cross-supplier refusal is deterministic (before the model) so it works offline and is always logged; the model additionally has no way to reach other suppliers' data.
- React effects must use block bodies around `scrollIntoView` (newer Chromium returns a Promise; an arrow body returned it as a "cleanup" and crashed the chat dock).
- pHash is corroborating only (weight 0.35, below the 0.6 flag threshold) and only within one supplier: measured on our template invoices, a different invoice on the same template has distance ~2 while a phone photo of the same invoice has ~8, so pHash alone cannot identify an invoice. Exact duplicates are caught by normalised number / IRN / SHA-256.
- Duplicates compare only against earlier invoices (lower id), so the original is never flagged as a copy of its resubmission; rejected invoices are ignored.
- AI bounding boxes come from our own positioned tokens on the line Claude cites, not model-estimated coordinates (more reliable highlights). On disagreement with the exact PDF text layer, the PDF text wins and the field goes to review.
- `AI_MODE=cached` lets the team pre-warm `backend/data/ai_cache/` with a key once and then demo with live-quality extraction fully offline. (Superseded 2026-11-13: no live API, see below.)
- Supplier to-dos are message codes + params from the server, rendered from i18n files; no internal data (approver names, SAP refs) is sent to suppliers. Language choice is a per-browser preference (localStorage).
- MSME clock starts at acceptance (GR/SES date) whatever the match outcome; traders excluded; no written agreement = 15 days.
- Dashboard, payment run, MSME guardian and controls report get their data from the seeded history (step 22); all are live queries, not placeholders.
- Recharts 3.10.1 (React 18 compatible, 0 audit findings).
- Audit events are written after commit in their own transaction (not inside the business transaction): guarantees no phantom events; the tiny risk is a crash between the two commits losing an event, acceptable for the demo and noted for production (outbox pattern).

- Supplier risk card is information only (never an engine input) and rule-based, not a score: each level comes with the rules that fired. Thresholds are labelled assumptions in `reports/supplier_risk.py` (`THRESHOLDS`): dispute rate 30% judged only from 10+ invoices (first-pass exception rates of 20-30% are normal in AP; at 20% every seeded supplier was "watch"), 2+ blocked duplicates, e-invoice compliance below 95%, bank change within 90 days. "Paid on time" measures Plant X's performance to the supplier. Sustainability records are fictional constants keyed by vendor code (no schema change, no reseed needed).

- ERS is set per PO, not per supplier (as SAP's ERS indicator on the PO item): switching all of Konkan to ERS would have changed the seeded history and broken the paper-invoice SoD demo on PO 4500001007. Under GST a registered supplier still issues the tax invoice for Plant X's input tax credit; Duly's ERS settlement drives the payment and the supplier's tax invoice would be linked to it (not built). Labelled in ASSUMPTIONS.md; verify the freight GST treatment with the tax team.

- Policy changes are made by one administrator with a written reason, versioned and audited; no second approver (maker-checker) for policy yet: noted as the production step in QA_PREP Q18. A change applies to new matches, approvals and payment runs; open invoices are not re-decided until something else re-runs their match (GR, correction, credit note).

- Credit notes are a separate table, not invoice rows with negative amounts: every invoice query (payment run, queue, dashboard, duplicates, risk, impact) would otherwise have to exclude them. They are entered in a form (no PDF parsing), accepted at once (they only reduce what Plant X owes) and allowed only before approval. Price-difference credit notes do not clear PRICE_VARIANCE (the line price is still above the PO; the clerk override covers that FLAG). The new Hindi string (`portal.enter_credit_note`, "क्रेडिट नोट दर्ज करें") and the changed QTY_EXCEEDS_GR line were written by Claude and should get a native-speaker review like the rest of hi.json.

- Email-in is a simulation: no IMAP/SMTP, so no SPF/DKIM/DMARC results; the sender check is domain-based against the vendor master only (a real deployment would add those). The supplier is always identified from the GSTIN on the invoice, never from the sender, so a spoofed email can at most be flagged, never mis-assign an invoice. Attachments are processed as the clerk who fetched the mail (recorded as processed_by, audited).

## Known bugs
- OCR can misread with high confidence (seen while tuning S12: GSTIN "24HXDPN..." read as "24HXOPN..." at >= 0.9 on a slightly different blur). Such a misread would not go to review; the engine would block GSTIN_INVALID / SUPPLIER_MISMATCH instead (safe, but not explained as an OCR issue). Consider a GSTIN check-digit failure on OCR text -> review item.
- Approver MFA secrets are random per seed: after every reset, approvers must scan the Overview QR again (in DEMO_SCRIPT.md).
- History: a few old duplicates stay BLOCKED forever (there is no clerk "reject a blocked invoice" action), so the 45+ day age bucket is never empty. Realistic, but a reject action for blocked invoices would be a small useful addition.
- The optional Claude API path (extraction and chat) has never been run against the live API; it is switched off by team decision (no credits). If anyone enables it, test it first.
- The browser pane in this environment is narrower than a laptop screen, so the three-pane layout was checked via DOM measurements at 1600 px (grid 488/390/390 px) and visually only in the stacked narrow layout.
- None known. Visual layout has been checked through the accessibility tree and DOM, not by eye (the browser pane could not take screenshots this session). Have a quick look at the login page and shell on first run.
- Gotcha (fixed): never call `queryClient.clear()` on identity change; it detaches the `me` observer. Use `switchIdentity` in `AuthContext.tsx`.
